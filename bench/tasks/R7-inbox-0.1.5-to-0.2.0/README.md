# R7: dsh-inbox, 0.1.5-rc.2 → 0.2.0-rc.2

| | |
|---|---|
| Plugin | `@chance722/dsh-inbox`, a paste inbox (capture, classify, browse, retrieve) with a browser panel |
| Repository | https://github.com/Chance722/dsh-inbox (MIT; `environment/fixture/LICENSE`) |
| Fixture | `a5f7a5229979`, the parent of the migration, with the `allowBuilds` value fix of `4649b0b93f87` |
| Reference solution | `1aeefdb6e0ae` to `62db02ecc741`, the migration and its same-day settings fix, as `solution/migration.patch` |
| Span | devDependencies at `^0.1.5-rc.2` (`dsh-web` pinned to `0.1.5-rc.2`), peer ranges `^0.1.5-rc.2` → 0.2.0-rc.2 |
| `--before` | `2026-09-30T05:17:07Z`, the last commit of the reference solution |

The plugin's peer ranges `^0.1.5-rc.2` do not admit 0.2.0-rc.2, so dsh 0.2.0-rc.2 refuses to install it (`dsh plugin add` checks every `@deepseek-ai/dsh*` peer with `semver.satisfies(..., { includePrerelease: true })`). Its code still typechecks against the 0.2.0-rc.2 packages, because it reaches the settings service through `ctx.get('settings')` cast to its own local interface. What breaks is behaviour at run time. dsh 0.2.0 replaces the settings service. A plugin no longer registers a settings namespace. Instead, `@deepseek-ai/dsh-settings` addresses the plugin's own profile row (`describe()`, and the async `update(ns, patch)` and `mutate(ns, ops)`) and writes only the fields that the plugin's exported `Config` marks `volatile()`. The plugin's namespace writes (`register`/`get`/`update('dsh-inbox-ui', ...)`) are rejected with "No configurable plugin entry". That rejection is never awaited, and dsh treats an unhandled rejection as fatal, so toggling the panel's list layout or saving the sync form crashes the host. The installer CLI (`dsh-inbox init`) also fails on 0.2.x, because it copies the `standard` preset into `$DSH_HOME/.agent-presets/`, which 0.2.0 no longer reads.

The author's migration commit `1aeefdb6e0ae` widens the peer ranges to `^0.1.5-rc.2 || ^0.2.0-rc.2`. It also moves the devDependencies to `0.2.0-rc.2` (and `cordis`/`schemastery` to `~4.0.4`/`~3.18.4`), exempts `@deepseek-ai/*` from pnpm's `minimumReleaseAge`, and makes `init` skip the preset steps when `dsh --version` reports 0.2 or later. Three hours later the author found the settings crash on the desktop runtime and fixed it in `62db02ecc741`. That commit adds `src/host/settings.ts`, which uses the namespace service when the runtime has `register`, and otherwise reads and writes the plugin's config row at `ctx.fiber.entry.options.id`. It also exports `Config` with the panel and sync fields marked live, turns a refused write into an answer instead of a throw, and makes the panel say when the list layout was not saved. The commits between the two change only documentation. The reference solution is the whole range, because the migration commit alone still crashes the host on the target. The patch is the whole range diff (`git diff --binary a5f7a5229979 62db02ecc741`, 20 files), regenerated against the fixture so that its one context line in `pnpm-workspace.yaml` reads `esbuild: true`. It includes the author's documentation updates in `AGENTS.md`, `README*.md` and `docs/help/`. Nothing else differs from the parent commit: the fixture keeps every path of it, there is no committed build output at that commit (`lib/` is git-ignored), and the repository has no `.agents/` or `.cursor/` directory. `AGENTS.md` and `CLAUDE.md` (which only includes `AGENTS.md`) are the project's standing conventions, written before this migration, and the code cites them.

The task has no hidden tests. The tests that the range changed or added all depend on how the author implemented the change. `test/cli.test.ts` tests the new `presetMechanism` export and its `directory`/`declaration`/`unknown` answers. `test/settings.test.ts` tests the new `src/host/settings.ts` module (`settingsStore`, `legacySettings`, `markLive`, `UI_SECTION`, `WEBDAV_FIELDS`). `test/ui-config.test.ts` fakes the 0.2.x service with only `describe()` and `update(id, patch)`, and requires the write to go to the row id read from `ctx.fiber.entry.options.id`. A correct migration that writes through `mutate`, finds its row another way, or names its helpers differently would fail these tests.

The fixture differs from `a5f7a5229979` in one line. In `pnpm-workspace.yaml`, the parent commit has pnpm's placeholder `allowBuilds: { esbuild: set this to true or false }`. pnpm ignores a non-boolean value, so with pnpm 11 every `pnpm install` exits with `ERR_PNPM_IGNORED_BUILDS` (esbuild 0.25.12 and 0.28.2), whatever dsh version is installed. The author found this later and fixed it in `4649b0b93f87` ("pnpm 11.10 already exited non-zero on every install"). The verifier fails every script when the install fails, so a first oracle run scored 0.15. The fixture therefore starts with that value set to `true`, as the author's later commit has it. The value fix has nothing to do with the dsh release.
