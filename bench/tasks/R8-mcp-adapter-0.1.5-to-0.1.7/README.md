dsh 0.1.7 replaces the settings model: a plugin no longer registers a settings namespace (`ctx.settings.register` is gone; the plugin's Loader-entry Config is the namespace, its id is the entry id, and live fields are `.volatile()`), `@deepseek-ai/dsh-settings` exports `SettingsForms` instead of `SettingsProvider`, the browser half reads its form through `ctx.configForms` instead of `ctx.settingsScope`, and `@deepseek-ai/dsh-client-runtime`, which the plugin's `dsh.client.inject` still names, was last published for 0.1.1. On 0.1.7-rc.2 the fixture's peer range refuses the target, `test/settings.test.js` fails on its import of `SettingsProvider`, and its host and client code are written against the removed settings API. The author's commit `e0821ee` ported the configuration to the entry Config model (an exported volatile `Config`, a `createMcpConfigScope` wrapper keeping the old `get/watch/update/mutate` surface, cross-field validation at consumption), moved the client to `configForms` with the entry id `mcp-adapter`, dropped the 0.1.1-rc.2 fallback and the `dsh-client-runtime` inject, added a one-time import of the legacy `mcp:` section of `settings.yaml`, and matched the nav-icon patch script to 0.1.7's renamed icons. That commit read the Config from `ctx.config`, which cordis 4 refuses (`cannot get property "config" without inject`), so every start that mounted the entry died; `3efb79a` reads it from the second `apply` argument instead. The reference solution is the range through `3efb79a`, which also contains the version bump `1d00aff`. It leaves out `225c1b7` ("mount the Settings RPC as exact /api Fetch routes"): it fixes `connection.rpc.handle`, whose code path in `@deepseek-ai/dsh-client-connection` is the same in 0.1.5-rc.1 and 0.1.7-rc.2 (as is cordis between 4.0.2 and 4.0.4), so the defect predates the span and is not something 0.1.7 forced; `27a3730` and later are features or the next span. The task has no `typecheck` script (`"typecheck": null`): the plugin is plain JavaScript.

The task has no hidden tests. The one test that fails on the target whatever the code, `test/settings.test.js`, was rewritten around the author's new API (`createMcpConfigScope`, `readMcpConfig`, `McpConfigSchema`); the client tests (`test/client-apply.test.js`, `test/client-settings-controller.test.js`) pin the namespace `mcp-adapter`, a choice (renaming the bundle's entry id to `mcp` would keep the old namespace) and drop the older-generation cases; `test/legacy-import.test.js` covers the legacy import, a feature the author added. A migration that makes other choices is not wrong, so those tests stay as the fixture had them and the agent must keep its own tests passing.

The oracle scores 1.0 and `nop` 0.44: the fixture fails `contract` (its peer range and devDependency refuse 0.1.7-rc.2) and `test` (`test/settings.test.js`), and passes `build` and `boot`. The unmigrated plugin still reaches `dsh web` ready on 0.1.7-rc.2 without a line the verifier counts as a failure, although its settings namespace and its Settings page do not work there; `boot` does not tell the fixture from the migration on this task.
